# parser3-amqp-demo

Демонстрационное тестовое приложение для класса `amqp` [Parser3](https://www.parser.ru/) — небольшой конвейер, который проверяет класс в реальных условиях (конкурирующие consumer'ы, рестарт брокера), плюс отдельный чек-лист, покрывающий большинство опций API.

## Что здесь

Небольшой пайплайн «забрать URL, записать метрику», целиком построенный на классе `amqp`:

```
dispatcher.html  --[очередь links]-->  monitor.html x2  --[очередь metrics]-->  alerter.html
                                        (конкурирующие consumer'ы)
```

- **`dispatcher.html`** — кладёт в очередь URL для обхода (реальные ID тем форума parser.ru), пачками по 20 с паузой между пачками. Каждое 10-е сообщение — отравленное (`{"url":"BADACK"}`), специально для проверки реального протокольного нарушения (см. ниже).
- **`monitor.html`** — запускается **в двух экземплярах одновременно**; они конкурируют за одну очередь (`qos prefetch_count(1)` у каждого, ручной ack). Каждый забирает URL через `curl`, публикует результат в очередь метрик и подтверждает. На `BADACK` намеренно подтверждает одно и то же сообщение дважды — это настоящая ошибка брокера (`PRECONDITION_FAILED - unknown delivery tag`), а не исключение Parser3.
- **`alerter.html`** — pull-режим (`count(-1)`, без callback), вычитывает очередь метрик раз в несколько секунд и логирует каждую — специально без callback, чтобы буфер между вызовами накапливался видимым образом.
- **`auto.p`** — общие вспомогательные методы: таблица имён очередей, простой лог.
- **`prepare.html`** — объявляет очереди и чистит их; запускать один раз перед свежей сессией.
- **`run.sh`** — убивает оставшиеся процессы, готовит очереди и запускает dispatcher + 2 × monitor + alerter в фоне.
- **`features.html`** — самостоятельный чек-лист, не связанный с пайплайном выше: последовательно проверяет опции `declare`/`bind`/`publish`/`consume`/`ack`/`nack`/`reject`/`qos`/`purge`/`info`/`delete` (включая публикацию сообщения со всеми возможными properties и headers всех типов, с последующей проверкой, что при `consume` возвращаются ровно те же значения). Запускается напрямую: `../parser3 features.html`.

## Запуск

Нужен запущенный RabbitMQ (`guest`/`guest`, `localhost:5672` по умолчанию) и сборка Parser3 с `WITH_AMQP` в ../.

```sh
./run.sh
tail -f logs/*.log
```

Остановить — `killall parser3`.

## `logs.demo/` — как выглядит самовосстановление на практике

Это настоящие, неотредактированные логи одного прогона, в середине которого вручную был на 3 секунды был выключен RabbitMQ — поверх обычной отравы сообщениями от dispatcher'а. В логах видны две независимые истории «сбой → восстановление», и обе обработаны целиком внутри класса `amqp`, без какого-либо особого кода в самом приложении.

**1. Отравленное сообщение — ошибка уровня канала, чинится без reconnect'а**

`monitor.log`:
```
17:40:02.138369 instance1 OK .../forum/?id=86908 ...
17:40:02.138741 instance1 BADACK poison: acked tag 6 once, acking again on purpose
17:40:02.139198 instance1 CONSUME ERROR: amqp: consume failed: PRECONDITION_FAILED - unknown delivery tag 6
17:40:02.588936 instance2 OK .../forum/?id=86909 ...
17:40:03.172394 instance1 OK .../forum/?id=86910 ...
```
Двойное подтверждение одного delivery tag — протокольное нарушение: брокер закрывает *канал* (не соединение) с `PRECONDITION_FAILED`. Следующая же операция `instance1` падает с этой ошибкой, но уже через ~1 секунду (`17:40:03.172`) всё снова работает как обычно — класс определяет, что ошибка канального уровня (не соединения), тихо переоткрывает только канал, и цикл consume продолжается. Без reconnect'а, без потери сообщений у `instance2`, который вообще ничего не заметил.

**2. Рестарт брокера — ошибка уровня соединения, `auto_reconnect(5)` сам восстанавливается**

`monitor.log`:
```
17:40:04.641118 instance2 FAIL {...} : amqp: publish failed: a socket error occurred
17:40:05.244420 instance1 FAIL {...} : amqp: publish failed: a socket error occurred
17:40:09.646350 instance2 CONSUME ERROR: amqp: open TCP socket failed: a socket error occurred
17:40:10.321048 instance1 CONSUME ERROR: amqp: open TCP socket failed: a socket error occurred
17:40:23.858560 instance2 OK .../forum/?id=86920 ...
17:40:23.860749 instance1 OK .../forum/?id=86921 ...
```
Тот же сбой независимо виден и в `dispatcher.log`, и в `alerter.log` (сокеты падают, пауза, и обычный трафик возобновляется примерно к `17:40:22`-`17:40:24`). Все три процесса были созданы с `auto_reconnect(5)` и сами ничего для этого не делали — класс классифицировал сбой как ошибку соединения, поспал 5 секунд и повторял попытки, пока брокер не вернулся, полностью самостоятельно. Каждый экземпляр восстановился независимо и продолжил работу.
